# 答辩准备讲稿

本文稿按 5 到 8 分钟答辩口径组织，适合先整体陈述，再配合系统演示和教师追问展开。

## 1. 开场自述

各位老师好，我的课程项目题目是“寻根溯源族谱管理系统”。本项目围绕数据库应用实践的要求完成，核心目标是支持多用户、多族谱的成员管理、关系维护、递归查询、统计分析和图形化展示，并在大规模模拟数据下完成 SQL 与索引性能验证。

## 2. 需求理解

我对本项目的理解可以概括为三点。

第一，这是一个典型的层级加图结构的数据管理系统。成员之间既有父母子女关系，也有婚姻关系，所以不能只按普通表单系统处理。

第二，课程要求不仅是做界面，更重要的是数据库建模、关系规范化、复杂 SQL、索引设计和性能分析。

第三，项目必须支持大规模模拟数据，包括 10 个族谱、总成员数超过 10 万，并且至少有 1 个族谱超过 5 万成员。

## 3. 数据库设计

在数据库设计上，我识别了 3 个核心实体和 3 个联系实体。

核心实体是：

- `user_account`
- `family_tree`
- `member`

联系实体是：

- `tree_collaborator`
- `parent_child`
- `marriage`

这样设计的原因是，用户和族谱之间存在创建与协作两类关系，成员之间又存在带属性的父母子女关系和婚姻关系，用独立关系表表达更符合关系模型，也更便于约束和查询。

在范式方面，我将各个关系模式整理并分析到第三范式。像 `parent_child` 这种关系表甚至满足 BCNF。整体设计中没有把非主属性错误地依赖到其他非主属性上，因此可以避免插入、删除和更新异常。

## 4. 约束设计

为了保证数据一致性，我做了三类约束。

第一类是主键、外键和唯一约束，用于保证实体标识和引用关系正确。

第二类是 `CHECK` 约束，例如：

- 性别只能取 `male`、`female`、`unknown`
- `death_date` 不能早于 `birth_date`
- 活着的成员不能有死亡日期
- 婚姻关系中 `member_id_1 < member_id_2`
- 同一孩子最多一个父亲和一个母亲

第三类是普通 `CHECK` 难以表达的业务约束。我通过 PostgreSQL 触发器防止祖先环路，避免出现“某个成员既是别人祖先又回到自己后代链上”的非法结构。

## 5. SQL 与查询实现

课程要求中的核心 SQL，我都按“单个 SQL”实现。

包括：

- 查询某成员的配偶和所有子女
- 用 Recursive CTE 查询所有祖先
- 统计平均寿命最长的一代
- 查询年龄大于 50 且没有配偶的男性成员
- 查询出生年份早于本代平均出生年份的成员

此外，我还扩展实现了：

- 姓名模糊查找
- 后代分支树查询
- 亲缘路径查询
- Dashboard 统计查询

这些查询中，祖先查询、分支查询和亲缘路径查询都明显体现了递归查询和图结构查询的特点。

## 6. 索引与性能优化

在索引设计方面，我没有只建单列索引，而是围绕真实查询场景设计了复合索引。

重点索引包括：

- `idx_member_tree_name`
- `idx_member_name_trgm`
- `idx_parent_child_tree_parent`
- `idx_parent_child_tree_child`
- `idx_marriage_tree_member1`
- `idx_marriage_tree_member2`

其中：

- `idx_member_name_trgm` 用于支持姓名模糊搜索
- `idx_parent_child_tree_parent` 用于支持根据父节点查询子节点和四代查询

在性能验证方面，我对两类场景做了索引前后对比：

- 姓名模糊查找
- 四代后代查询

并通过 `EXPLAIN ANALYZE` 观察执行计划变化，说明索引确实改善了扫描方式和查询耗时。

## 7. 数据生成与导入导出

为了满足课程对大规模数据的要求，我没有手工插入数据，而是编写了 Python 数据生成脚本。

数据生成的特点是：

- 生成 10 个族谱
- 总成员数超过 10 万
- 至少 1 个族谱超过 5 万成员
- 单个族谱至少 30 代
- 每个成员都处在可解释的关系结构中

数据生成后导出为 CSV，再使用 PostgreSQL 的 `COPY` 做批量导入。为了课程演示方便，我还补充了：

- 一键重导入脚本
- 分支导出脚本
- 本机环境下的快速导入流程

## 8. 系统实现与演示

系统实现上，我采用的是前后端分离架构。

- 前端：Vue 3 + Vite + Pinia
- 后端：FastAPI + SQLAlchemy
- 数据库：PostgreSQL
- 辅助组件：Redis

界面功能包括：

- 用户登录与注册
- 族谱管理
- 协作者管理
- 成员管理
- Dashboard 统计
- 模糊查找
- 祖先查询
- 分支树查询
- 亲缘关系查询

其中祖先查询、分支树和亲缘路径支持结构化展示，并兼顾大规模数据下的可读性。

## 9. 项目亮点

我认为这个项目的亮点主要有四点。

第一，数据库设计和业务场景结合比较紧，不是机械画 ER 图。

第二，复杂 SQL 部分比较完整，尤其是 Recursive CTE 和路径查询。

第三，数据规模达到了课程要求，并且有完整的数据生成、导入和导出链路。

第四，除了数据库本体，我还完成了界面、缓存、批量导入导出和查询优化，使项目具备较完整的演示形态。

## 10. 结束语

整体来说，这个项目完成了课程要求中的数据库建模、关系规范化、约束设计、复杂 SQL、索引优化、大规模数据处理和图形化演示等核心内容。后续如果继续扩展，我会重点考虑进一步优化亲缘路径查询性能，以及补充更完善的导出与统计分析能力。

## 11. 高频追问参考回答

### 11.1 为什么选 PostgreSQL

因为 PostgreSQL 对 Recursive CTE、复杂聚合、复合索引、`pg_trgm` 模糊检索和 `EXPLAIN ANALYZE` 支持比较成熟，和本项目的层级递归查询、路径查询以及性能分析要求高度匹配。

### 11.2 为什么不用纯 ORM 写复杂查询

因为祖先查询、分支树查询和亲缘路径查询本质上是递归和图遍历问题，用 ORM 强行表达会降低可读性，也不利于答辩时直接展示 SQL。课程又要求提交 SQL，所以复杂查询采用原生 SQL 更合适。

### 11.3 如何证明满足 3NF

我在数据库设计文档里逐表分析了函数依赖。每个表的非主属性都只依赖于主键，不依赖其他非主属性，也不存在传递依赖，因此满足 3NF。像 `parent_child` 这种关系表甚至满足 BCNF。

### 11.4 你做了哪些约束

除了主键、外键和唯一约束，我还加了多个 `CHECK` 约束，例如生卒年合法性、性别枚举、婚姻关系有序性，以及同一孩子最多一个父亲和一个母亲。另外还通过触发器防止祖先环路。

### 11.5 你做了哪些性能优化

主要做了两类优化。

第一类是数据库索引优化，重点是成员姓名模糊索引和父节点查子节点索引。

第二类是系统层优化，对高频接口接入 Redis 缓存，同时在大规模数据导入时采用 `COPY` 和快速重导入方案。

### 11.6 为什么要做 Docker

当前最终交付版本不再依赖 Docker，主要是考虑到本机磁盘占用和课程项目的实际需求。本项目最终采用本机直接运行 PostgreSQL、Redis、FastAPI 和 Vue 的方式，更轻量，也更符合当前演示环境。
