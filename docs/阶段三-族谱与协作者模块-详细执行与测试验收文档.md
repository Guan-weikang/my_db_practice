# 阶段三：族谱与协作者模块详细执行与测试验收文档

## 1. 文档目的

本文档用于细化《[寻根溯源族谱管理系统-总开发计划](/home/mochen/db_practice/docs/寻根溯源族谱管理系统-总开发计划.md)》中的“阶段三：族谱与协作者模块”，作为后续实际实施、联调和验收的执行依据。

本阶段以阶段一已完成的工程基线、阶段二已完成的认证与权限基线为前提，重点解决“族谱作为核心业务对象可被真实管理”和“协作者角色边界在业务接口中正式生效”两类问题，为阶段四成员与关系模块提供稳定的业务容器和访问范围。

## 2. 阶段目标

本阶段的目标是让项目具备完整可用的族谱管理与协作能力，具体包括：

- 完成族谱创建、列表、详情、修改、删除五项核心能力。
- 完成“当前用户可访问族谱”查询能力，并统一分页和响应结构。
- 完成协作者列表、邀请、角色修改、权限撤销四项能力。
- 将 `creator`、`collaborator`、`reader` 三类角色正式落地到真实业务接口，而不再只停留在权限依赖样例层。
- 建立族谱详情页和协作者管理页的最小前后端联调闭环。
- 为阶段四成员、关系、搜索、统计等模块提供统一的 `tree_id` 访问入口和角色约束基线。

## 3. 当前基线判断

结合当前仓库状态，阶段三开始前的业务基线如下：

- 阶段一的配置、错误响应、健康检查、测试基座已具备。
- 阶段二的注册、登录、刷新、登出、当前用户识别和族谱角色权限依赖已具备。
- `backend/app/api/routers/family_trees.py` 已有路由骨架，`GET /`、`GET /accessible`、`GET /{tree_id}` 已有最小实现，但 `POST`、`PATCH`、`DELETE` 仍为占位逻辑。
- `backend/app/api/routers/collaborators.py` 仍全部为占位实现。
- `backend/app/repositories/family_tree_repository.py` 与 `backend/app/repositories/collaborator_repository.py` 已有部分读能力基础，但缺少完整业务服务编排。
- 前端 `FamilyTreeListView`、`FamilyTreeDetailView`、`CollaboratorManageView` 仍是骨架页面。
- 前端认证基线已完成，因此阶段三可以直接在登录态之上接入业务列表、详情和协作者管理。

因此，本阶段的重点不是重新设计权限体系，而是把阶段二的认证与权限能力真正嵌入族谱和协作者业务流中，形成首个完整的业务闭环。

## 4. 范围与边界

### 4.1 本阶段范围

- 族谱模块接口契约与响应结构收口
- 族谱创建、列表、详情、修改、删除实现
- 当前用户可访问族谱查询实现
- 协作者列表、邀请、角色修改、撤销实现
- 族谱角色边界在真实业务接口中的全面落地
- 前端族谱列表页、详情页、协作者管理页最小联调
- 阶段三测试数据、接口测试和前端手工验收用例建设
- 阶段三相关文档与联调说明收口

### 4.2 本阶段不做

- 不进入成员 CRUD 与父母子女、婚姻关系维护
- 不实现祖先递归查询、亲缘路径查询、树形预览和复杂搜索
- 不实现 Dashboard 统计分析
- 不实现 CSV 导入导出和大规模模拟数据
- 不扩展邮件邀请、邀请链接确认、协作者自助接受邀请等复杂协作流程

说明：

- 当前阶段的“邀请协作者”定义为“由创建者直接把某用户加入目标族谱的协作范围并赋予角色”，不引入独立邀请确认流程。
- `tree_collaborator.status` 中的 `pending` 仅作为未来扩展保留，本阶段默认以 `active` 和 `revoked` 两种业务状态完成闭环即可。

## 6. 详细执行任务

## 6.1 工作包 A：族谱与协作者接口契约收口

目标：

- 在实现前固定阶段三的后端接口契约、角色边界和列表返回结构，避免实现过程中反复改动。

具体任务：

- 对照《[前后端目录结构与接口模块划分文档](/home/mochen/db_practice/docs/前后端目录结构与接口模块划分文档.md)》固定以下接口：
  - `GET /api/v1/family-trees/`
  - `POST /api/v1/family-trees/`
  - `GET /api/v1/family-trees/accessible`
  - `GET /api/v1/family-trees/{tree_id}`
  - `PATCH /api/v1/family-trees/{tree_id}`
  - `DELETE /api/v1/family-trees/{tree_id}`
  - `GET /api/v1/family-trees/{tree_id}/collaborators/`
  - `POST /api/v1/family-trees/{tree_id}/collaborators/`
  - `PATCH /api/v1/family-trees/{tree_id}/collaborators/{user_id}`
  - `DELETE /api/v1/family-trees/{tree_id}/collaborators/{user_id}`
- 固定列表接口统一返回结构：
  - `items`
  - `total`
  - `page`
  - `page_size`
- 固定族谱字段范围，建议本阶段至少覆盖：
  - `tree_name`
  - `surname`
  - `compiled_at`
  - `description`
- 固定协作者返回字段，建议本阶段至少覆盖：
  - `user_id`
  - `username`
  - `display_name`
  - `access_role`
  - `status`
  - `invited_by`
  - `invited_at`
- 固定角色边界：
  - `creator`：可读、可改、可删族谱，可管理协作者
  - `collaborator`：可读、可改族谱，不可删族谱，不可管理协作者
  - `reader`：仅可读，不可修改族谱，不可管理协作者

输出物：

- 阶段三接口清单
- 请求响应模型清单
- 角色能力矩阵

完成定义：

- 前后端在开始开发前，对阶段三接口、字段和权限边界无歧义。

目标：

- 让族谱模块具备可维护的 schema、repository、service 分层边界，避免路由层直接堆业务逻辑。

具体任务：

  - `FamilyTreeCreateRequest`
  - `FamilyTreeUpdateRequest`
  - `FamilyTreeDetailResponse`
  - `AccessibleFamilyTreeListItem`
  - `PaginatedFamilyTreeResponse`
- 视需要补齐 `compiled_at` 可写支持。
- 梳理 `backend/app/repositories/family_tree_repository.py`，明确以下数据访问能力：
  - 按 `tree_id` 查询
  - 按创建者查询
  - 按当前用户可访问范围查询
  - 创建族谱

- 新增或补齐 `backend/app/services/family_tree_service.py`，承接：

  - 业务异常转换
  - 创建后默认角色归属处理
  - 统一响应对象拼装
- 明确“创建族谱后是否在协作者表中额外写入 creator 记录”的策略，并在实现前固定。

建议策略：

- `creator` 身份以 `family_tree.creator_user_id` 为准，不额外在 `tree_collaborator` 写入 `creator` 记录。
- 协作者表只承载 `collaborator` 与 `reader` 两种授权关系。

输出物：

- 族谱 schema 设计
- repository 与 service 职责边界说明
- 族谱创建与访问范围设计说明

完成定义：

- 路由层只负责收参、鉴权、调服务，族谱业务逻辑不再散落在多个入口。

## 6.3 工作包 C：可访问族谱列表与族谱详情实现

目标：

- 先完成“看得到什么”的闭环，为后续修改、删除、协作者管理提供统一入口。

具体任务：

- 实现 `GET /api/v1/family-trees/` 与 `GET /api/v1/family-trees/accessible` 的最终策略，并固定是否保留双接口。

建议策略：

- `GET /api/v1/family-trees/` 作为当前用户可访问族谱的标准列表接口。
- `GET /api/v1/family-trees/accessible` 可兼容保留，但应明确为别名接口，避免双份业务逻辑。

- 列表结果需同时覆盖：
  - 当前用户创建的族谱
  - 当前用户作为 `collaborator` 的族谱
  - 当前用户作为 `reader` 的族谱
- 列表结果需返回当前用户在该族谱下的 `access_role`。
- 支持基础分页参数：
  - `page`
  - `page_size`
- 支持基础排序策略并固定默认排序。

建议默认排序：

- 按 `updated_at DESC, tree_id DESC` 返回。

- 实现 `GET /api/v1/family-trees/{tree_id}`：
  - 读权限用户可访问
  - 返回族谱基础信息
  - 返回当前用户角色
  - 可视情况预留 `collaborator_count` 等聚合字段，但非必需

输出物：

- 可访问族谱列表接口
- 族谱详情接口
- 分页与排序约定

完成定义：

- 登录用户能够稳定获取自己可见的族谱集合，并能打开任一有权限访问的族谱详情。

## 6.4 工作包 D：族谱创建、修改与删除实现

目标：

- 让族谱对象真正可管理，并把修改与删除能力严格约束到正确角色。

具体任务：

- 实现 `POST /api/v1/family-trees/`：
  - 仅要求登录
  - 自动把 `current_user.user_id` 写为 `creator_user_id`
  - 返回创建后的族谱详情或标准创建响应
- 实现 `PATCH /api/v1/family-trees/{tree_id}`：
  - 允许 `creator`、`collaborator` 修改
  - 不允许 `reader` 修改
  - 只允许更新本阶段开放字段
- 实现 `DELETE /api/v1/family-trees/{tree_id}`：
  - 仅允许 `creator`
  - 明确删除策略

建议删除策略：

- 本阶段优先采用物理删除，但必须先确认数据库外键与后续阶段成员表、关系表的影响。
- 如果当前数据库约束或后续扩展风险较高，可改为“阶段三先禁止删除已有成员的族谱，待阶段四后统一设计级联删除策略”。

推荐执行取舍：

- 若当前族谱下尚无成员和关系数据，可允许物理删除。
- 一旦引入成员、关系、统计等依赖表，后续阶段应重新评估是否切换为软删除或受限删除。

- 补齐以下异常场景：
  - 族谱不存在
  - 无权限访问
  - 更新字段非法
  - 重复或空名称等输入异常

输出物：

- 族谱创建接口
- 族谱更新接口
- 族谱删除接口
- 删除规则说明

完成定义：

- `creator` 与 `collaborator` 的写能力差异在族谱接口中真实生效，删除能力只保留给 `creator`。

## 6.5 工作包 E：协作者管理闭环实现

目标：

- 让创建者能够管理当前族谱的访问者，并形成完整授权闭环。

具体任务：

- 补齐 `backend/app/schemas/collaborator.py`：
  - `CollaboratorCreateRequest`
  - `CollaboratorUpdateRequest`
  - `CollaboratorResponse`
  - `PaginatedCollaboratorResponse`
- 实现 `GET /api/v1/family-trees/{tree_id}/collaborators/`：
  - 至少允许 `creator` 查看
  - 是否允许 `collaborator`、`reader` 查看需要在实现前固定

建议策略：

- 本阶段默认仅允许 `creator` 查看完整协作者列表，避免普通协作者无明确业务需要却暴露人员信息。

- 实现 `POST /api/v1/family-trees/{tree_id}/collaborators/`：
  - 仅 `creator`
  - `access_role` 只允许 `collaborator` 或 `reader`
  - 不允许邀请自己
  - 不允许邀请族谱创建者
  - 对已存在且 `active` 的授权做冲突处理
  - 对已 `revoked` 的授权可选择恢复而不是重复插入
- 实现 `PATCH /api/v1/family-trees/{tree_id}/collaborators/{user_id}`：
  - 仅 `creator`
  - 允许在 `collaborator` 与 `reader` 之间切换
  - 不允许把他人提升为 `creator`
  - 不允许修改创建者记录
- 实现 `DELETE /api/v1/family-trees/{tree_id}/collaborators/{user_id}`：
  - 仅 `creator`
  - 建议将记录状态更新为 `revoked`
  - 撤销后该用户立即失去该族谱访问权

建议实现策略：

- 协作者记录默认保留历史，不做物理删除。
- 撤销使用 `status = 'revoked'`。
- 重新授权同一用户时优先复用旧记录并恢复为 `active`。

输出物：

- 协作者列表接口
- 协作者邀请接口
- 协作者角色修改接口
- 协作者权限撤销接口
- 协作者状态流转说明

完成定义：

- 创建者能够对协作者完成增、查、改、撤销全流程，且权限边界稳定。

## 6.6 工作包 F：真实业务权限落地与越权防护补强

具体任务：

- 统一族谱接口的权限接入方式：
  - 列表接口要求登录
  - 详情接口要求 `require_tree_reader`

- 统一协作者接口权限接入方式：

- 核对无权限时的状态码与错误码是否统一为阶段一、二约定格式。
- 补齐业务服务中对下列越权情况的显式防护：
  - 无权用户读取他人族谱详情
  - `reader` 修改族谱
  - `collaborator` 删除族谱
  - `collaborator` 管理协作者
  - 跨族谱修改他人授权

输出物：

- 阶段三权限接入矩阵
- 越权场景清单
- 权限拒绝错误约定

完成定义：

- 阶段三所有新增接口都能用同一套权限规则解释，且不存在明显越权空洞。

- 更新后的业务说明文档
- 联调说明
- 阶段三详细文档

完成定义：

- 阅读者能够清楚区分“阶段三已完成业务闭环”和“阶段四开始才进入的成员与关系能力”。

## 7. 推荐执行顺序

建议按以下顺序推进实施：

1. 工作包 A：族谱与协作者接口契约收口
2. 工作包 B：族谱数据模型与服务边界收口
3. 工作包 C：可访问族谱列表与族谱详情实现
4. 工作包 D：族谱创建、修改与删除实现
5. 工作包 E：协作者管理闭环实现
6. 工作包 F：真实业务权限落地与越权防护补强
7. 工作包 G：前端族谱列表、详情与协作者管理最小联调
8. 工作包 H：阶段三测试数据、自动化测试与手工验收用例建设
9. 工作包 I：文档、联调说明与阶段边界收口

原因：

- 先固定契约和服务边界，才能避免前后端联调时反复返工。
- 先完成列表和详情，能够尽早验证“可访问范围”这一阶段三核心能力。
- 协作者管理必须建立在稳定的族谱主对象与权限依赖之上。
- 前端联调应放在后端接口、错误码和角色边界基本稳定后接入。

## 8. 阶段三验收标准

阶段三完成时，必须同时满足以下条件：

### 8.1 族谱接口验收

- `GET /api/v1/family-trees/` 可返回当前用户可访问族谱列表。
- `GET /api/v1/family-trees/{tree_id}` 可返回指定族谱详情。
- `POST /api/v1/family-trees/` 可成功创建族谱。
- `PATCH /api/v1/family-trees/{tree_id}` 可按角色规则更新族谱。
- `DELETE /api/v1/family-trees/{tree_id}` 仅创建者可执行，并符合既定删除规则。

### 8.2 协作者接口验收

- `GET /api/v1/family-trees/{tree_id}/collaborators/` 可返回协作者列表。
- `POST /api/v1/family-trees/{tree_id}/collaborators/` 可新增或恢复授权。
- `PATCH /api/v1/family-trees/{tree_id}/collaborators/{user_id}` 可在 `collaborator` 与 `reader` 间切换角色。
- `DELETE /api/v1/family-trees/{tree_id}/collaborators/{user_id}` 可撤销协作者访问权。

### 8.3 权限边界验收

- 用户只能看到自己创建或被授权的族谱。
- `creator` 可管理协作者并可删除族谱。
- `collaborator` 可读写族谱但不可删谱，也不可管理协作者。
- `reader` 只能读取族谱详情，不可修改数据。
- 无权限用户无法访问目标族谱详情和协作者接口。

### 8.4 前端联调验收

- 登录后可进入族谱列表页并看到当前用户可访问族谱。
- 可从族谱列表进入详情页。
- 创建者可进入协作者管理页并完成授权操作。
- 权限不足用户在前端有明确拦截或提示，不出现误导性可操作入口。

### 8.5 文档与测试验收

- 阶段三接口、角色边界、错误码、测试命令有文档说明。
- 自动化测试至少覆盖成功路径、越权失败路径和关键边界路径。
- 阶段三边界明确，不混入成员、关系、搜索、统计等后续业务实现。

## 9. 测试计划与用例

## 9.1 可访问族谱列表测试

测试目标：

- 验证用户只能看到自己可访问的族谱，并能拿到正确角色。

前置条件：

- 测试数据库中存在多个用户、多个族谱和不同角色授权记录。

执行步骤：

1. 准备创建者、自身协作者、自身读者、无权限四类场景数据。
2. 使用不同用户分别调用 `GET /api/v1/family-trees/`。
3. 检查返回条目和 `access_role`。

预期结果：

- 返回结果只包含当前用户有权访问的族谱。
- 每条记录的 `access_role` 与数据库授权关系一致。
- 无权限族谱不会泄露到列表中。

## 9.2 族谱详情读取测试

测试目标：

- 验证读权限边界和详情字段返回正确。

执行步骤：

1. 使用 `creator`、`collaborator`、`reader` 分别请求 `GET /api/v1/family-trees/{tree_id}`。
2. 使用无权限用户请求同一接口。
3. 请求不存在的 `tree_id`。

预期结果：

- 有读权限的三类角色都能成功获取详情。
- 无权限用户返回统一 `403` 错误。
- 不存在的族谱返回统一 `404` 错误。

## 9.3 族谱创建测试

测试目标：

- 验证登录用户可创建族谱，且创建后自动成为该族谱创建者。

执行步骤：

1. 使用正常登录用户调用 `POST /api/v1/family-trees/`。
2. 查询数据库中的 `creator_user_id`。
3. 再调用列表接口检查新族谱是否出现。

预期结果：

- 创建成功。
- `creator_user_id` 等于当前登录用户。
- 新族谱可立即出现在当前用户可访问列表中，角色为 `creator`。

## 9.4 族谱更新权限测试

测试目标：

- 验证不同角色的更新边界。

执行步骤：

1. 由 `creator` 更新族谱名称或描述。
2. 由 `collaborator` 更新同一族谱。
3. 由 `reader` 更新同一族谱。
4. 由无权限用户更新同一族谱。

预期结果：

- `creator` 与 `collaborator` 更新成功。
- `reader` 与无权限用户被拒绝。
- 错误结构统一。

## 9.5 族谱删除测试

测试目标：

- 验证删除仅允许创建者执行，并符合既定删除规则。

执行步骤：

1. 由 `creator` 删除目标族谱。
2. 由 `collaborator` 删除目标族谱。
3. 由 `reader` 删除目标族谱。
4. 删除后再次请求该族谱详情。

预期结果：

- 仅 `creator` 删除成功。
- 其他角色删除被拒绝。
- 删除后的详情请求返回符合设计的不存在或不可访问结果。

## 9.6 协作者邀请测试

测试目标：

- 验证协作者授权流程、角色限制和冲突处理正确。

执行步骤：

1. 由 `creator` 邀请一个新用户为 `collaborator`。
2. 再邀请一个新用户为 `reader`。
3. 邀请已是 `active` 协作者的用户。
4. 邀请创建者本人。
5. 邀请不存在用户。

预期结果：

- 合法邀请成功。
- `access_role` 仅允许 `collaborator` 或 `reader`。
- 已存在 `active` 授权的重复邀请被拒绝或按约定返回冲突。
- 邀请创建者本人被拒绝。
- 不存在用户被稳定拒绝。

## 9.7 协作者角色切换测试

测试目标：

- 验证创建者可在两类协作者角色间切换，且不允许越界提升权限。

执行步骤：

1. 将某用户从 `reader` 改为 `collaborator`。
2. 再从 `collaborator` 改回 `reader`。
3. 尝试把用户改成 `creator`。
4. 尝试修改族谱创建者的角色。

预期结果：

- 合法切换成功。
- 不能把任何协作者改成 `creator`。
- 不能通过协作者接口修改创建者身份。

## 9.8 协作者撤销测试

测试目标：

- 验证撤销权限后用户立即失去访问能力。

执行步骤：

1. 准备一个 `active collaborator` 或 `active reader`。
2. 由 `creator` 调用撤销接口。
3. 被撤销用户再次请求该族谱详情或列表。
4. 检查数据库中的协作者状态。

预期结果：

- 撤销成功。
- 被撤销用户立刻失去访问权限。
- 协作者状态按约定更新为 `revoked`。

## 9.9 协作者接口越权测试

测试目标：

- 验证非创建者无法管理协作者。

执行步骤：

1. 由 `collaborator` 调用协作者列表、邀请、修改、撤销接口。
2. 由 `reader` 调用同一组接口。
3. 由无权限用户调用同一组接口。

预期结果：

- 三类用户全部被拒绝。
- 返回统一 `403` 错误。
- 无协作者信息泄露。

## 9.10 前端联调手工验收测试

测试目标：

- 验证阶段三前端主流程可演示。

执行步骤：

1. 使用创建者账号登录。
2. 打开族谱列表页，查看可访问族谱。
3. 创建新族谱并进入详情页。
4. 进入协作者管理页，添加一个读者用户。
5. 使用读者账号登录并验证仅可读。
6. 使用协作者账号登录并验证可编辑但不可删谱、不可管协作者。

预期结果：

- 主要页面可连续流转。
- 页面展示与后端权限一致。
- 无明显阻塞性跳转错误或状态错乱。

## 10. 测试数据准备建议

为保证阶段三测试稳定，建议至少准备以下固定测试数据：

- 激活用户 4 到 5 个
- 其中 1 个为主创建者用户
- 其中 1 个为协作者用户
- 其中 1 个为只读用户
- 其中 1 个为无权限用户
- 族谱 2 到 3 个
- 其中 1 个族谱用于完整覆盖协作者授权、改权、撤销流程
- 其中 1 个族谱仅由创建者可见，用于验证列表隔离

说明：

- 阶段三测试数据应继续保持小规模、强确定性。
- 不需要引入阶段七的大规模模拟数据。
- 阶段四开始可在此基础上继续挂接成员与关系测试数据。

## 11. 阶段三完成后的状态定义

阶段三完成后，项目应处于以下状态：

- 创建者已经可以完成协作者授权、改权与撤销闭环。

换句话说，阶段三完成的标志不是“查询很多”，而是“核心业务对象成立、权限边界真正落地、后续模块有了稳定容器”。
