# 数据库结构与查询优化说明

## 1. 文档目的

本文档用于整理当前项目在数据库结构、约束设计、索引设计、递归查询、路径查询、批量导入和缓存配合方面已经完成的优化工作，并说明各项优化的出发点、早期做法与当前改进方案。

本文档重点回答以下问题：

- 数据库结构上做了哪些优化
- 为了保证数据一致性增加了哪些约束和触发器
- 查询层面做了哪些优化
- 大规模数据导入做了哪些优化
- 哪些优化已经落地，哪些仍属于可选增强项

## 2. 优化总览

当前项目的数据库优化主要分为四类：

1. 结构优化
2. 约束与一致性优化
3. 索引与查询优化
4. 批量导入与缓存配合优化

这些优化共同服务于以下目标：

- 在十万级成员数据下保持可接受的查询性能
- 支撑递归查询、图遍历查询和统计查询
- 保证族谱关系数据的业务一致性
- 降低大规模测试数据导入和重导入成本

## 3. 数据库结构优化

## 3.1 从“普通成员表”到“关系拆分建模”

### 早期思路

如果只从界面录入角度出发，最直接的做法是把父亲、母亲、配偶等信息直接冗余放在成员表中，例如：

- `member.father_id`
- `member.mother_id`
- `member.spouse_id`

这种写法实现简单，但问题明显：

- 无法自然表达多次婚姻
- 无法表达父母角色的约束
- 不适合后续递归祖先查询和亲缘路径搜索
- 更新时容易造成冗余和不一致

### 当前做法

项目最终采用关系拆分建模：

- `member`：只保存成员自身属性
- `parent_child`：独立保存父母子女关系
- `marriage`：独立保存婚姻关系
- `tree_collaborator`：独立保存族谱协作关系

### 改进效果

- 关系语义更清晰
- 更符合第三范式
- 方便为关系单独建索引
- 更适合递归查询和路径查询

## 3.2 从“固定层级思维”到“递归友好结构”

### 早期思路

如果按普通家谱录入表的思路，可能会倾向于把“第 1 代、第 2 代、第 3 代”写成固定层级结构，或者在应用层手工循环查父母子女。

### 当前做法

项目采用：

- `parent_child(tree_id, parent_member_id, child_member_id, parent_role)`
- PostgreSQL Recursive CTE

这使得祖先查询、后代查询不依赖固定代数，而是支持：

- 30 代以上递归追溯
- 可控最大深度
- 面向树和图结构的统一查询接口

### 改进效果

- 能满足课程要求中的不固定深度祖先追溯
- 结构与 SQL 递归查询天然匹配
- 比应用层手写多轮查询更稳定、可控

## 4. 约束与一致性优化

## 4.1 主键、外键、唯一约束

### 早期思路

在原型阶段，如果只保证“能写入数据”，往往只会建最少的主键，而忽略关系表的复合约束。

### 当前做法

当前库中已经系统设置了：

- 主键约束
- 外键约束
- 唯一约束

典型例子：

- `tree_collaborator` 使用组合主键 `(tree_id, user_id)`
- `member` 使用 `UNIQUE(tree_id, member_id)`，用于支撑复合外键
- `parent_child` 使用组合主键 `(tree_id, parent_member_id, child_member_id, parent_role)`
- `parent_child` 额外约束 `UNIQUE(tree_id, child_member_id, parent_role)`，保证同一孩子最多一个父亲、一个母亲
- `marriage` 使用组合主键 `(tree_id, member_id_1, member_id_2)`

### 改进效果

- 防止重复授权、重复亲子关系、重复婚姻关系
- 保证关系只能在同一族谱内建立
- 为查询优化提供更稳定的数据基础

## 4.2 CHECK 约束优化

### 早期思路

如果只在前端或服务层做校验，数据库仍可能被绕过直接写入非法数据。

### 当前做法

当前数据库已设置多类 `CHECK` 约束，例如：

- `gender IN ('male', 'female', 'unknown')`
- `death_date >= birth_date`
- `is_alive = FALSE OR death_date IS NULL`
- `generation_no > 0`
- `parent_member_id <> child_member_id`
- `parent_role IN ('father', 'mother')`
- `member_id_1 <> member_id_2`
- `member_id_1 < member_id_2`
- `status IN ('active', 'ended')`

后续还补充了婚姻生命周期约束：

- `married_at IS NULL OR ended_at IS NULL OR ended_at >= married_at`
- `status <> 'active' OR ended_at IS NULL`
- `status <> 'ended' OR ended_at IS NOT NULL`

### 改进效果

- 把数据合法性下沉到数据库层
- 降低应用层漏校验带来的脏数据风险
- 后续统计和查询不需要反复处理明显非法记录

## 4.3 祖先环路触发器优化

### 早期思路

最初如果只依赖应用层判断，很容易出现：

- A 是 B 的父亲
- B 又被错误地设置成 A 的祖先链上的父亲

一旦形成环路，祖先查询、后代查询和亲缘路径搜索都会出现逻辑错误甚至无限递归风险。

### 当前做法

数据库中增加了触发器：

- `prevent_parent_child_cycle()`
- `trg_prevent_parent_child_cycle`

该触发器在 `parent_child` 插入或更新前运行，通过递归检查阻止祖先环路。

### 改进效果

- 保证关系图在血缘维度上仍是合法有向无环结构
- 避免递归 SQL 被错误数据拖垮
- 比“仅在应用层约束”更稳

## 5. 索引优化

## 5.1 从“只有主键索引”到“按真实查询模式建索引”

### 早期思路

如果只依赖主键和默认唯一索引，那么：

- 姓名模糊查找会慢
- 父节点查子节点会慢
- 婚姻双向查配偶会慢
- 深分页排序会慢

### 当前做法

项目按真实查询场景建立了以下关键索引。

### 5.1.1 族谱与协作者相关

- `idx_family_tree_creator`
- `idx_tree_collaborator_user_status_tree`
- `idx_tree_collaborator_tree_status_user`

用途：

- 支撑用户可访问族谱列表查询
- 支撑协作者分页与角色过滤

### 5.1.2 成员基础查询相关

- `idx_member_tree_name`
- `idx_member_tree_generation`
- `idx_member_tree_gender_birth`
- `idx_member_name_trgm`

用途：

- 同族谱内按姓名查找
- 按辈分统计
- 按性别和出生日期筛选
- `%关键字%` 姓名模糊查找

### 5.1.3 父母子女关系相关

- `idx_parent_child_tree_parent`
- `idx_parent_child_tree_child`

用途：

- 根据父节点查子节点
- 根据子节点查父母
- 支撑祖先递归和后代递归

### 5.1.4 婚姻关系相关

- `idx_marriage_tree_member1`
- `idx_marriage_tree_member2`

用途：

- 双向查找配偶
- 支撑未婚男性统计
- 支撑亲缘路径中的婚姻边搜索

## 5.2 从“基础索引”到“排序索引优化”

### 早期做法

成员列表分页按：

- `generation_no`
- `birth_date`
- `member_id`

排序，但数据库最初只有：

- `idx_member_tree_generation`

这意味着在大族谱深分页场景下，数据库仍可能：

- 先扫描大量成员
- 再额外排序
- 在大 offset 下出现明显开销

### 当前做法

后来补充了复合排序索引：

- `idx_member_tree_generation_birth_member`

定义为：

```sql
(tree_id, generation_no ASC NULLS LAST, birth_date ASC NULLS LAST, member_id ASC)
```

### 改进效果

- 更贴合成员列表的真实排序顺序
- 降低大页码翻页时的排序成本
- 对 5 万级族谱列表更友好

## 5.3 从“全婚姻索引”到“活跃婚姻部分索引”

### 早期做法

婚姻关系最初只有：

- `idx_marriage_tree_member1`
- `idx_marriage_tree_member2`

但很多查询实际上只关心：

- `status = 'active'`

例如：

- 当前配偶查询
- 亲缘路径中默认只走有效婚姻边

### 当前做法

补充了部分索引：

- `idx_marriage_tree_member1_active`
- `idx_marriage_tree_member2_active`

### 改进效果

- 缩小活跃婚姻查询的索引范围
- 对亲缘路径和当前婚姻查询更有针对性
- 比单纯依赖全量婚姻索引更高效

## 6. 查询优化

## 6.1 祖先查询优化

### 早期思路

祖先查询如果用应用层循环，会出现：

- 多轮数据库往返
- 难以控制去重与环路
- 代码复杂且深度不稳定

### 当前做法

当前祖先查询使用：

- PostgreSQL Recursive CTE
- `idx_parent_child_tree_child`
- 路径数组 `path_member_ids`
- `NOT parent_member_id = ANY(path_member_ids)` 做路径内去重

### 改进效果

- 单条 SQL 完成递归祖先追溯
- 天然支持可配置 `max_depth`
- 与触发器一起避免祖先环路干扰

## 6.2 后代分支查询优化

### 早期思路

后代树如果完全在应用层按节点逐层查询，会产生大量 N+1 查询。

### 当前做法

后代分支查询同样使用 Recursive CTE：

- 从根成员出发递归展开
- 使用 `path_member_ids` 防止路径内重复
- 使用 `max_depth` 控制分支范围

### 改进效果

- 分支树可以一次性按结构取回
- 减少频繁数据库往返
- 方便前端直接渲染结构化树

## 6.3 亲缘路径查询优化

## 6.3.1 从“单向扩展”到“双向 BFS”

### 早期思路

亲缘关系查询如果只从成员 A 单向广搜到成员 B，在大族谱里会遇到明显问题：

- 扩展节点数过多
- 最大跳数一高就变慢
- 很容易超时或失败

### 当前做法

当前亲缘路径查询采用双向 BFS 思路：

- 一端从 `member_a` 开始扩展
- 另一端从 `member_b` 开始扩展
- 每轮优先扩展当前更小的 frontier
- 当两边搜索相遇时立刻拼接路径

邻居加载使用统一 SQL：

- 既查父到子
- 也查子到父
- 还查婚姻双向边

### 改进效果

- 明显降低高跳数路径搜索的爆炸式扩展
- 比单向 BFS 更适合大规模族谱
- 对“存在但距离较远”的关系链查询更稳

## 6.3.2 从“血缘树思维”到“图遍历思维”

### 早期思路

如果只把族谱看成单棵树，那么婚姻关系会被忽略，亲缘路径就不完整。

### 当前做法

当前路径搜索把两类边统一纳入图遍历：

- `parent_child`
- `marriage`

并在返回结果时额外补充：

- 路径节点详情
- 路径边类型
- 父母角色
- 婚姻状态

### 改进效果

- 查询结果更符合真实亲缘链路
- 不再局限于单树递归
- 适合前端图形化路径展示

## 6.4 成员模糊搜索优化

## 6.4.1 从“普通 like 查询”到 trigram 索引

### 早期做法

成员搜索的核心需求是：

- 支持按姓名模糊搜索
- 支持 `%关键字%`

如果只使用普通 `LIKE` 或只建 `(tree_id, name)` 索引，那么对于任意子串匹配帮助有限。

### 当前做法

项目启用了 PostgreSQL `pg_trgm` 扩展，并建立：

- `idx_member_name_trgm`

用于加速：

- `ILIKE '%keyword%'`

### 改进效果

- 模糊查找比普通顺序扫描更有优化空间
- 满足课程要求中的模糊姓名查询与性能对比

## 6.4.2 从“一次性大聚合”到“两段式搜索”

### 早期做法

最初搜索 SQL 直接：

1. 先筛所有命中成员
2. 同时关联 `parent_child`
3. 再关联父母成员表
4. 聚合出父母姓名
5. 最后分页

这种写法的问题是：

- 即使只看第一页，也要为所有命中结果做父母聚合
- 当命中结果较大时，排序和聚合都偏重

### 当前做法

当前改为“两段式搜索”：

1. 第一段只在 `member` 表中筛选、排序、分页，并统计总数
2. 第二段只针对当前页的 `member_id` 去补父母姓名

### 改进效果

- 减少对大批量命中集合的无效 join 和聚合
- 更贴合分页接口的真实访问模式
- 对大族谱中的高频搜索更友好

## 6.5 统计查询优化

### 早期做法

统计查询主要依赖全表扫描和聚合，如果没有：

- 合适的过滤索引
- 统一缓存策略

则在高频刷新 Dashboard 时容易重复计算。

### 当前做法

统计类 SQL 保持单条 SQL 实现，同时结合：

- `idx_member_tree_gender_birth`
- `idx_member_tree_generation`
- Redis 热点缓存

覆盖的查询包括：

- 家族总人数与男女比例
- 平均寿命最长的一代
- 大于 50 岁未婚男性
- 早于本代平均出生年份成员

### 改进效果

- 结构上仍满足课程“单个 SQL”要求
- 高频读取时由缓存削峰
- 在不引入物化汇总表的情况下保持实现简单

## 7. 大规模数据导入优化

## 7.1 从“逐条插入”到 `COPY`

### 早期思路

如果十万级数据逐条插入：

- 太慢
- 事务日志开销大
- 导入时间不可接受

### 当前做法

阶段七数据统一采用：

- Python 规则生成 CSV
- PostgreSQL `COPY` 批量导入

### 改进效果

- 导入效率远高于逐条写入
- 更适合课程要求中的十万级模拟数据

## 7.2 从“重复手工清库导入”到一键重导入脚本

### 早期做法

重导入阶段七数据时，如果手工执行：

- 删关系
- 删成员
- 删用户
- 再逐表导入

流程复杂且容易出错。

### 当前做法

项目增加了一键重导入脚本：

- [reimport_generated.py](/home/mochen/db_practice/scripts/stage7/reimport_generated.py:1)

该脚本会自动：

- 清理旧的阶段七数据
- 逐表重导 CSV
- 清理 Redis 业务缓存

### 改进效果

- 演示环境重置成本更低
- 数据重导更可重复

## 7.3 从“导入后直接查询”到导入后 `ANALYZE`

### 早期做法

大规模 `COPY` 导入完成后，如果立即查询，但不更新统计信息，查询优化器可能基于旧统计信息生成较差执行计划。

### 当前做法

当前重导入脚本在导入结束后主动执行：

- `ANALYZE user_account`
- `ANALYZE family_tree`
- `ANALYZE tree_collaborator`
- `ANALYZE member`
- `ANALYZE parent_child`
- `ANALYZE marriage`

### 改进效果

- 让优化器尽快获得新的表分布信息
- 降低导入后第一批查询走偏计划的概率

## 7.4 从“约束全开导入”到可信离线数据的快速导入

### 早期做法

在大规模导入时如果保留所有触发器和约束逐行检查，尤其是 `parent_child` 的环路触发器，会导致导入明显变慢。

### 当前做法

重导入脚本对可信的阶段七离线 CSV 启用：

- `SET session_replication_role = replica`

导入完成后恢复：

- `SET session_replication_role = origin`

### 改进效果

- 跳过不必要的逐行触发器检查
- 对阶段七这种“规则生成且可信”的数据集，导入速度明显提升

## 8. 缓存与数据库配合优化

虽然缓存不属于纯数据库结构优化，但它直接影响数据库压力，因此这里一并说明。

### 早期做法

所有查询都直接打数据库，结果是：

- Dashboard 统计重复计算
- 同一树详情重复读取
- 成员列表分页被反复访问
- 祖先和亲缘高频样例会持续打数据库

### 当前做法

项目对高频读接口引入 Redis 缓存，重点覆盖：

- 族谱列表和详情
- 成员 ID 范围
- 成员分页列表
- Dashboard 统计
- 祖先查询
- 分支树查询
- 亲缘路径查询

写操作后会按 `tree_id` 维度失效相关缓存。

### 改进效果

- 减少热点查询对数据库的重复压力
- 对手工联调和答辩演示更稳定
- 避免把数据库优化完全寄托在单次 SQL 上

## 9. 仍可继续优化的方向

当前项目已经完成课程要求和演示需求下的主要优化，但仍有一些可选增强项。

### 9.1 可继续做但当前未强制落地

- 将“大于 50 岁未婚男性”查询进一步改写为更适合索引的日期比较表达式
- 为 `lower(name)` 建 trigram 函数索引
- 对极深分页改为游标分页
- 为亲缘路径建立预计算邻接边表
- 为祖先/后代查询建立闭包表
- 为高频统计建立物化汇总表

### 9.2 为什么当前没有继续过度优化

原因主要有三点：

1. 本项目目标是课程交付，不是生产级家谱平台
2. 当前数据规模下，现有结构、索引、CTE、双向 BFS 和缓存已经足够支撑答辩与联调
3. 过度引入闭包表、物化汇总、分区表等会显著增加写入复杂度和维护成本

## 10. 总结

当前项目的数据库优化已经形成比较完整的一条线：

- 在结构上，将成员属性与关系拆分建模
- 在一致性上，补齐主键、外键、唯一约束、`CHECK` 约束和祖先环路触发器
- 在索引上，围绕模糊搜索、父查子、子查父、婚姻双向查询、深分页排序等场景持续补强
- 在查询上，使用 Recursive CTE、双向 BFS、两段式分页搜索等更适合大规模家谱数据的方法
- 在导入上，使用 `COPY`、快速重导、导入后 `ANALYZE` 和可信数据快速导入策略
