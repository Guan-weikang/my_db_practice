# 阶段二：认证与权限闭环详细执行与测试验收文档

## 1. 文档目的

本文档用于细化《[寻根溯源族谱管理系统-总开发计划](/home/mochen/db_practice/docs/寻根溯源族谱管理系统-总开发计划.md)》中的“阶段二：认证与权限闭环”，作为后续实际实施、联调和验收的执行依据。

本阶段以阶段一已经完成的工程基线为前提，重点解决“用户身份可信”和“访问边界可控”两类问题，为阶段三及之后的族谱、成员、协作者等业务模块提供统一认证与权限入口。

## 2. 阶段目标

本阶段的目标是让项目具备完整的认证闭环和最小可复用的权限控制能力，具体包括：

- 完成用户注册、登录、刷新令牌、登出、当前用户信息五项基础认证能力。
- 固化 `JWT Access Token + Refresh Token` 双令牌方案。
- 使用 `Argon2` 完成密码哈希与校验。
- 建立后端统一的当前用户依赖、令牌解析校验和族谱角色权限判断入口。
- 建立前端最小登录态管理、路由守卫和登录状态恢复能力。
- 让后续受保护接口可以直接复用阶段二沉淀的认证与权限基座。

## 3. 当前基线判断

结合当前仓库状态，阶段二开始前的认证与权限基线如下：

- 后端 `backend/app/api/routers/auth.py` 已存在路由骨架，但 `register`、`refresh`、`logout`、`me` 仍为占位实现。
- 后端 `backend/app/services/auth_service.py` 仅具备简单签发令牌能力，尚未接入数据库用户校验、Refresh Token 状态管理和业务异常处理。
- 后端 `backend/app/core/security.py` 已具备密码哈希与 JWT 签发基础，但缺少令牌解码、类型校验、过期处理和统一 claim 约定。
- 后端 `backend/app/api/deps/auth.py` 当前只返回原始 token，尚未解析出真实用户，也未校验用户状态。
- 后端 `backend/app/api/deps/permission.py` 仍是简化占位逻辑，尚未接入族谱角色查询与统一错误结构。
- 数据模型中 `user_account`、`tree_collaborator` 已具备阶段二可复用的基础字段。
- 前端 `frontend/src/stores/auth.ts` 只保存内存中的 `accessToken`、`refreshToken`，没有用户资料、持久化和状态恢复。
- 前端 `frontend/src/router/index.ts` 尚未落地路由守卫。
- 前端 `frontend/src/api/auth.ts` 仅有 `login`、`register` 两个接口封装，缺少 `refresh`、`logout`、`me`。

因此，阶段二的重点不是“重新设计认证方案”，而是把现有骨架打通为可运行、可验证、可复用的认证与权限闭环。

## 4. 范围与边界

### 4.1 本阶段范围

- 后端认证接口闭环实现
- JWT claim 与签发校验规则收口
- 密码哈希、密码校验和用户状态校验
- Refresh Token 状态存储、失效和登出处理
- 当前用户依赖与受保护接口接入
- 族谱级角色权限判断入口建设
- 前端登录态管理、路由守卫、状态恢复和基础鉴权拦截
- 阶段二对应测试、联调说明和验收文档

### 4.2 本阶段不做

- 不完成族谱 CRUD、协作者管理、成员管理等完整业务模块
- 不提前实现阶段三之后的完整页面交互与业务流程
- 不引入复杂 RBAC 后台系统，只围绕本项目的族谱角色模型落地
- 不做统计缓存、复杂查询优化、模拟数据生成和部署收尾

## 6. 详细执行任务

## 6.1 工作包 A：认证领域模型与接口契约收口

目标：

- 先固定阶段二所有输入输出结构、错误码和接口边界，避免后续实现反复改口。

具体任务：

- 明确认证模块正式接口为：
  - `POST /api/v1/auth/register`
  - `POST /api/v1/auth/login`
  - `POST /api/v1/auth/refresh`
  - `POST /api/v1/auth/logout`
  - `GET /api/v1/auth/me`
- 收口 `backend/app/schemas/auth.py`、`backend/app/schemas/user.py` 的请求与响应模型。
- 明确 `TokenResponse` 是否返回：
  - `access_token`
  - `refresh_token`
  - `token_type`
  - `expires_in`
- 明确 `register` 成功后的返回策略，建议直接返回用户信息与令牌，或返回用户信息后由前端跳登录，二选一后固定。
- 明确认证相关统一错误码，至少包括：
  - `INVALID_CREDENTIALS`
  - `TOKEN_EXPIRED`
  - `TOKEN_INVALID`
  - `TOKEN_REVOKED`
  - `USER_DISABLED`
  - `USERNAME_ALREADY_EXISTS`
  - `EMAIL_ALREADY_EXISTS`
  - `AUTHENTICATION_REQUIRED`
  - `PERMISSION_DENIED`

输出物：

- 阶段二接口约定
- 认证错误码清单
- 请求响应示例

完成定义：

- 前后端对认证接口、返回结构、失败场景和错误码不再存在歧义。

## 6.2 工作包 B：用户注册链路落地

目标：

- 让新用户可以通过正式接口完成注册，并保证账号唯一性与密码安全。

具体任务：

- 在 `backend/app/api/routers/auth.py` 中将 `register` 从骨架改为真实业务入口。
- 在 `backend/app/services/auth_service.py` 中补齐注册流程：
  - 校验用户名是否已存在
  - 校验邮箱是否重复
  - 校验用户状态默认值
  - 使用 `Argon2` 生成 `password_hash`
  - 创建 `user_account`
- 在 `backend/app/repositories/user_repository.py` 中补齐以下基础方法：
  - `get_by_username`
  - `get_by_email`
  - `get_by_id`
  - `create`
- 明确注册字段的最小校验规则：
  - `username` 长度与字符约束
  - `password` 最小长度
  - `display_name` 非空
  - `email` 格式合法时才允许入库
- 决定是否允许注册后自动登录，并在文档中固定。

输出物：

- 用户注册业务链路
- 注册输入校验规则
- 唯一性冲突错误响应示例

完成定义：

- 新用户可注册成功，重复用户名或邮箱能被稳定拒绝，密码不会明文入库。

## 6.3 工作包 C：登录与令牌签发闭环

目标：

- 基于真实用户数据完成登录校验，并签发可区分用途的 Access/Refresh Token。

具体任务：

- 完成 `POST /api/v1/auth/login` 的真实校验逻辑：
  - 根据用户名查询用户
  - 校验用户状态是否为 `active`
  - 使用 `Argon2` 校验密码
  - 失败时返回统一认证错误
- 收口 `backend/app/core/security.py` 的 token 载荷约定，建议至少包含：
  - `sub`
  - `type`
  - `exp`
  - `iat`
  - 可选 `jti`
- 明确 `access token` 与 `refresh token` 的差异：
  - 使用不同 secret 或不同 claim
  - 有不同过期时间
  - `type` 必须可区分
- 明确 Access Token 的 subject 使用 `user_id` 还是 `username`，建议固定为 `user_id`，避免用户名修改影响令牌主体识别。
- 统一登录成功响应结构，并为前端后续登录态恢复预留用户信息载荷方案。

输出物：

- 登录业务链路
- JWT claim 设计说明
- 登录成功/失败响应示例

完成定义：

- 正确用户名密码可登录，错误密码、禁用用户、无效用户均被稳定拒绝，返回结构统一。

## 6.4 工作包 D：Refresh Token 存储、刷新与登出失效

目标：

- 形成真正可控的 Refresh Token 生命周期，而不是只靠 JWT 自身过期。

具体任务：

- 明确 Refresh Token 状态存储方案，优先采用 Redis。
- 明确 Redis 中的存储键设计，建议包含：
  - 用户维度
  - token 标识或摘要
  - 过期时间
- 决定 Refresh Token 存储策略：
  - 存原文
  - 存摘要
  - 单设备单 token
  - 单用户多 token
- 完成 `POST /api/v1/auth/refresh`：
  - 校验 token 类型为 `refresh`
  - 校验签名与过期时间
  - 校验 Redis 中状态仍有效
  - 签发新 Access Token
  - 视策略决定是否轮换 Refresh Token
- 完成 `POST /api/v1/auth/logout`：
  - 至少使当前 Refresh Token 失效
  - 若采用轮换策略，明确旧 token 处理方式
- 明确刷新和登出接口的请求载荷方式：
  - 请求体传 `refresh_token`
  - 或使用 HttpOnly Cookie
  - 当前阶段若继续前后端分离简单实现，建议优先使用请求体传 token，并在后续部署阶段再评估 Cookie 方案

输出物：

- Refresh Token 生命周期设计
- Redis 键与失效策略说明
- 刷新、登出接口约定

完成定义：

- Refresh Token 可以续期，登出后被登出的 Refresh Token 不能继续刷新。

## 6.5 工作包 E：当前用户依赖与受保护接口接入

目标：

- 建立所有受保护接口统一复用的认证依赖，避免各路由重复解析 token。

具体任务：

- 改造 `backend/app/api/deps/auth.py`：
  - 从 `OAuth2PasswordBearer` 获取 Bearer Token
  - 解码 Access Token
  - 校验 token 类型为 `access`
  - 读取用户 ID
  - 查询数据库中的当前用户
  - 校验用户状态
  - 返回统一的当前用户对象，而不是原始 token 字典
- 增加诸如以下依赖函数：
  - `get_current_user`
  - `get_current_active_user`
  - 可选 `get_optional_current_user`
- 将 `GET /api/v1/auth/me` 改为当前用户信息接口。
- 选择 1 到 2 个后续业务接口作为阶段二的受保护入口验证样例，建议优先接入：
  - `GET /api/v1/auth/me`
  - `GET /api/v1/family-trees/accessible` 或 `GET /api/v1/users/{user_id}`
- 统一未携带 token、token 非法、token 过期、用户不存在、用户被禁用时的错误返回。

输出物：

- 可复用认证依赖
- 当前用户信息接口
- 受保护接口接入样例

完成定义：

- 受保护接口在未登录或令牌异常情况下会被统一拒绝，登录后可识别真实用户身份。

## 6.6 工作包 F：族谱角色权限判断入口建设

目标：

- 把“是否已登录”和“是否有该族谱权限”分开，形成后续业务可直接复用的权限入口。

具体任务：

- 改造 `backend/app/api/deps/permission.py`，不再使用简单的 `actual_role` 传参占位方式。
- 设计基于 `tree_id` + `user_id` 的权限判定入口，兼容两类来源：
  - `family_tree.created_by` 对应的 `creator`
  - `tree_collaborator` 中的 `collaborator` / `reader`
- 明确角色映射规则：
  - 创建者默认拥有最高权限
  - 协作者可写
  - 只读用户不可写
- 设计可复用的权限依赖，建议包括：
  - `require_tree_reader`
  - `require_tree_editor`
  - `require_tree_creator`
- 统一权限不足时返回 `403` 与 `PERMISSION_DENIED`。
- 为阶段三预留接口复用方式，避免届时在各业务服务中重复拼权限判断。

输出物：

- 族谱权限判断设计
- 权限依赖入口
- 角色与能力映射表

完成定义：

- 后续族谱、成员、协作者模块可以直接通过权限依赖控制 `creator`、`collaborator`、`reader` 的访问边界。

2. 工作包 B：用户注册链路落地
3. 工作包 C：登录与令牌签发闭环

5. 工作包 E：当前用户依赖与受保护接口接入
6. 工作包 F：族谱角色权限判断入口建设
7. 工作包 G：前端登录态管理与路由守卫

- 前端守卫和状态恢复必须等待后端认证接口与错误码基本稳定后再接入。

## 8. 阶段二验收标准

阶段二完成时，必须同时满足以下条件：

### 8.1 认证接口验收

- `POST /api/v1/auth/register` 可完成用户注册。
- `POST /api/v1/auth/login` 可完成登录并返回有效令牌。
- `POST /api/v1/auth/refresh` 可使用有效 Refresh Token 获取新令牌。
- `POST /api/v1/auth/logout` 能使当前 Refresh Token 失效。
- `GET /api/v1/auth/me` 在登录后可返回当前用户资料。

### 8.2 安全与数据验收

- 密码仅以 `Argon2` 哈希形式存储。
- Access Token 与 Refresh Token 在 claim 或 secret 上有明确区分。
- 用户被禁用时不能登录，已有无效会话不能继续通过用户校验。
- 未授权、令牌非法、令牌过期、令牌失效和权限不足场景返回统一错误结构。

### 8.3 权限基线验收

- 至少已有一类受保护接口严格要求登录。
- 已存在可复用的族谱权限依赖入口。
- `creator`、`collaborator`、`reader` 的判定规则已经在后端固定。

### 8.4 前端联调验收

- 前端可完成注册或登录主流程。
- 登录态在刷新页面后可恢复。
- 未登录访问受保护页面会被拦截并跳转到登录页。
- Access Token 过期时，前端可按既定策略尝试刷新。

### 8.5 文档与基线验收

- 认证接口、错误码、请求示例、测试命令都有文档说明。
- 阶段二边界明确，不混入阶段三完整业务 CRUD 实现。

## 9. 测试计划与用例

## 9.1 后端注册服务测试

测试目标：

- 验证注册逻辑的唯一性校验、密码哈希和默认状态设置。

前置条件：

- 测试数据库可用。
- 用户表为空或已知状态可控。

执行步骤：

1. 使用合法用户名、密码、显示名和邮箱调用注册服务。
2. 查询数据库中的新用户记录。
3. 分别使用重复用户名、重复邮箱再次提交注册。

预期结果：

- 首次注册成功。
- 数据库中保存的是 `password_hash`，不是明文密码。
- 重复用户名或邮箱被拒绝，并返回统一冲突错误。

## 9.2 登录 API 测试

测试目标：

- 验证登录接口在成功、失败和用户禁用场景下行为正确。

执行步骤：

1. 准备一个正常用户和一个禁用用户。
2. 使用正确用户名密码调用 `POST /api/v1/auth/login`。
3. 使用错误密码再次调用。
4. 使用禁用用户调用。

预期结果：

- 正确凭证返回 Access/Refresh Token。
- 错误密码返回统一认证失败错误。
- 禁用用户返回 `USER_DISABLED` 或等价错误码。

## 9.3 JWT 校验与当前用户依赖测试

测试目标：

- 验证 Access Token 能正确解析为当前用户，异常令牌能被拒绝。

执行步骤：

1. 用合法 Access Token 请求 `GET /api/v1/auth/me`。
2. 不带 token 请求。
3. 带格式错误 token 请求。
4. 带过期 token 请求。
5. 带错误类型的 Refresh Token 请求需要 Access Token 的接口。

预期结果：

- 合法 token 可获取当前用户信息。
- 缺失 token、非法 token、过期 token、错误类型 token 均被拒绝。
- 错误结构统一，状态码与错误码匹配。

## 9.4 Refresh Token 刷新测试

测试目标：

- 验证 Refresh Token 可用于续期，失效 token 不能重复使用。

执行步骤：

1. 登录获得一组 token。
2. 使用 Refresh Token 调用 `POST /api/v1/auth/refresh`。
3. 对登出后的 Refresh Token 再次调用刷新。
4. 对伪造或过期的 Refresh Token 调用刷新。

预期结果：

- 有效 Refresh Token 能换取新令牌。
- 已登出或已失效的 Refresh Token 不能继续刷新。
- 伪造或过期 token 被稳定拒绝。

## 9.5 登出失效测试

测试目标：

- 验证登出操作至少能废弃当前 Refresh Token。

执行步骤：

1. 登录后保留 Refresh Token。
2. 调用 `POST /api/v1/auth/logout`。
3. 再用同一 Refresh Token 调用刷新。

预期结果：

- 登出成功。
- 被登出的 Refresh Token 不能再次刷新。

## 9.6 权限依赖测试

测试目标：

- 验证族谱权限依赖能正确区分未登录、无权限和不同角色。

执行步骤：

1. 准备 `creator`、`collaborator`、`reader`、无权限用户四类测试用户。
2. 对要求读权限的样例接口发起请求。
3. 对要求写权限的样例接口发起请求。
4. 对要求创建者权限的样例接口发起请求。

预期结果：

- `creator` 拥有最高权限。
- `collaborator` 满足读写但不满足创建者专属能力。
- `reader` 仅满足读取能力。
- 无权限用户返回 `403`。

## 9.7 前端登录态恢复测试

测试目标：

- 验证前端刷新页面后能够恢复登录态，并与 `/auth/me` 保持一致。

执行步骤：

1. 在前端完成登录。
2. 刷新浏览器页面。
3. 检查 store、当前用户状态和受保护页面访问结果。

预期结果：

- 刷新后能够恢复登录态。
- 当前用户信息可重新加载。
- 不出现刷新后被错误踢回登录页的抖动问题。

## 9.8 前端路由守卫测试

测试目标：

- 验证匿名访问与受保护路由跳转逻辑正确。

执行步骤：

1. 未登录访问 `/auth/login`、`/auth/register`。
2. 未登录直接访问 Dashboard、族谱列表、成员页等路由。
3. 登录后再次访问受保护路由。

预期结果：

- 匿名可访问登录与注册页。
- 匿名访问受保护页会被重定向到登录页。
- 登录后可进入受保护页。

## 9.9 认证错误响应结构测试

测试目标：

- 验证认证相关失败场景都符合阶段一统一错误结构。

执行步骤：

1. 制造注册冲突、登录失败、token 过期、权限不足等场景。
2. 检查响应体字段。

预期结果：

- 响应体统一包含：
  - `code`
  - `message`
  - `details`
- 不再混用 FastAPI 默认错误结构与自定义错误结构。

## 10. 测试数据准备建议

为保证阶段二测试稳定，建议至少准备以下固定测试数据：

- 普通激活用户 2 到 3 个
- 禁用用户 1 个
- 由其中 1 个用户创建的测试族谱 1 个
- 该测试族谱下的：
  - `creator`
  - `collaborator`
  - `reader`
  - 无权限用户

说明：

- 阶段二测试数据应保持小而确定，不引入阶段七的大规模模拟数据。
- 权限测试以“少量用户 + 单族谱”即可覆盖核心路径。

## 11. 阶段二完成后的状态定义

阶段二完成后，项目应处于以下状态：

- 系统已经具备可用的用户注册、登录、刷新、登出和当前用户识别能力。
- 后续任何业务接口都可以直接挂接统一的登录校验与族谱权限依赖。
- 前端已经具备最小可用的登录态管理能力，能够支撑阶段三开始的业务联调。

换句话说，阶段二完成的标志不是“业务功能多”，而是“身份可信、边界明确、后续可复用”。

## 12. 后续衔接

阶段二完成后，下一阶段应直接进入“阶段三：族谱与协作者模块”，重点推进以下内容：

- 族谱 CRUD
- 当前用户可访问族谱列表
- 协作者邀请、角色修改、权限撤销
- `creator`、`collaborator`、`reader` 在真实业务接口中的全面落地

阶段三的详细文档应默认以本阶段输出的认证依赖、权限依赖、错误结构和前端登录态基线为前提继续展开。
