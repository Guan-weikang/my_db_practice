# 阶段一：工程基线与开发环境收口详细执行与测试验收文档

## 1. 文档目的

本文档用于细化《[寻根溯源族谱管理系统总开发计划](/home/mochen/db_practice/docs/寻根溯源族谱管理系统-总开发计划.md)》中的“阶段一：工程基线与开发环境收口”，作为后续实际实施、联调和验收的执行依据。

本阶段只处理“工程基线稳定”和“开发环境可复现”问题，不进入完整业务功能实现，不提前实现阶段二及之后的业务逻辑。

## 2. 阶段目标

本阶段的目标是让项目具备稳定、可重复、可验证的开发基线，具体包括：

- 前后端项目都能在本地独立启动。
- 数据库结构可以通过迁移或初始化脚本一键落地。
- 后端具备统一配置入口、统一错误响应和基础健康检查能力。
- 前端具备稳定的环境变量、接口基地址和构建能力。
- 项目具备最小可执行测试基座，后续阶段可以在此基础上持续扩展。
- 文档、命令、目录职责与仓库实际状态一致。

## 3. 当前基线判断

结合当前仓库状态，本阶段已经具备但仍需收口的内容如下：

- 已具备前后端骨架目录。
- 已具备 PostgreSQL 主表、索引、Alembic 初始迁移和独立 SQL 初始化脚本。
- 已具备后端 `.env`、前端 `.env.*` 和 README 基础说明。
- 已具备健康检查路由骨架。
- 已具备测试目录，但缺少可执行测试样例和统一测试约定。
- 后端路由、服务、权限和错误处理仍大量处于骨架状态。
- `deploy/`、`docker-compose.yml`、统一日志策略、统一错误模型、分页约定、测试说明尚未收口。

因此，本阶段的重点不是“从零搭架子”，而是把已有骨架转成“稳定工程基线”。

## 4. 范围与边界

### 4.1 本阶段范围

- 环境配置与依赖版本收口
- 数据库初始化与迁移链路收口
- 后端应用启动基线收口
- 前端开发与构建基线收口
- 统一错误响应结构与基础接口约定收口
- 健康检查与基础日志能力收口
- 测试基座与最小测试样例建设
- 启动文档、执行文档和目录职责说明修订

### 4.2 本阶段不做

- 不完成注册、登录、刷新令牌、登出业务闭环
- 不完成族谱、成员、协作者、关系模块完整 CRUD
- 不完成复杂查询、统计分析和数据生成脚本
- 不完成完整 Docker 化部署，只允许输出部署基线清单和后续占位目录

## 5. 交付物

本阶段完成后，至少应产出以下成果：

1. 可运行的后端基础工程
2. 可构建的前端基础工程
3. 已验证可执行的数据库迁移流程
4. 统一错误响应结构文档与基础实现
5. 基础健康检查接口
6. 后端与前端环境变量说明
7. 最小测试基座与基础冒烟测试
8. 更新后的 README 或阶段执行说明
9. 阶段一执行记录与测试结果记录

## 6. 详细执行任务

## 6.1 工作包 A：环境与依赖收口

目标：

- 明确本地开发必需依赖、推荐版本和安装顺序。

具体任务：

- 核对 `backend/requirements/base.txt`、`backend/pyproject.toml`、`frontend/package.json` 的依赖是否与架构文档一致。
- 校验 `backend/.env.example`、`frontend/.env.example` 是否覆盖最小开发所需配置。
- 对 README 中 Python、Node.js、PostgreSQL、Redis 版本说明进行统一。
- 明确本机开发方案为主、Docker Compose 为后续阶段补齐的约定。

输出物：

- 更新后的依赖与环境说明文档。
- 补齐后的 `.env.example` 模板。

完成定义：

- 新同学仅依据 README 和 `.env.example` 就能完成本地环境准备。

## 6.2 工作包 B：数据库初始化链路收口

目标：

- 让数据库结构初始化路径明确且可重复执行。

具体任务：

- 固化两条官方初始化路径：
  - Alembic 迁移：`alembic upgrade head`
  - 直接 SQL 初始化：`scripts/sql/family_tree_init.sql`
- 说明两条路径的适用场景，默认以后端开发使用 Alembic 为主。
- 校验 `family_tree_db` 的表、索引、触发器与迁移文件一致。
- 明确后续数据库结构变更必须走 Alembic 增量迁移，不允许手工漂移。

输出物：

- 数据库初始化说明。
- 已验证的执行命令列表。

完成定义：

- 在空库上执行初始化后，可得到完整基础 schema。

## 6.3 工作包 C：后端启动基线收口

目标：

- 后端应用具备稳定启动、统一配置读取和基础探活能力。

具体任务：

- 校验 `app/main.py` 的应用创建流程，明确路由注册、中间件注册和后续异常处理入口。
- 统一 `app/core/config.py` 的配置读取方式和默认值策略。
- 收口数据库连接工厂和 `AsyncSession` 注入方式。
- 确保 `/api/v1/health/` 为基础探活接口，返回结构稳定。
- 补充后端启动失败时的最小诊断信息输出。

输出物：

- 可正常启动的 FastAPI 基线。
- 健康检查接口响应约定。

完成定义：

- `uvicorn app.main:app --reload` 可成功启动，访问健康检查可返回预期 JSON。

## 6.4 工作包 D：统一错误响应与基础接口约定收口

目标：

- 为后续所有业务接口建立一致的错误与基础响应规范。

具体任务：

- 固化统一错误结构：
  - `code`
  - `message`
  - `details`
- 统一 400/401/403/404/409/500 的错误编码命名策略。
- 明确成功响应中列表接口的分页结构预留方案：
  - `items`
  - `total`
  - `page`
  - `page_size`
- 在文档层先固定接口约定，基础实现只需覆盖健康检查和后续最先接入的接口。

输出物：

- 基础接口约定文档。
- 统一错误响应示例。

完成定义：

- 后续阶段任何接口实现都不需要再次讨论错误格式和基础分页格式。

## 6.5 工作包 E：日志与可观测性最小基线

目标：

- 建立最小可观测性能力，便于后续排查启动和接口问题。

具体任务：

- 明确日志入口文件与初始化方式。
- 约定日志至少区分：
  - 应用启动日志
  - 请求处理日志
  - 数据库异常日志
  - 认证异常日志
- 明确当前阶段只要求基础控制台日志，不要求接入 Prometheus/Grafana。
- 为健康检查保留后续扩展字段空间，但当前只返回最小状态结果。

输出物：

- 日志初始化约定。
- 当前阶段日志字段说明。

完成定义：

- 启动、访问健康检查、数据库连接失败等场景下可以看到基本诊断日志。

## 6.6 工作包 F：前端开发基线收口

目标：

- 前端能稳定安装、启动和构建，且能正确读取 API 地址配置。

具体任务：

- 校验 `VITE_API_BASE_URL` 与 Axios 客户端配置。
- 确认路由、Pinia、基础布局和主入口文件可正常启动。
- 明确前端当前阶段不要求完成功能页面，只要求工程可运行、路由可加载、构建成功。
- 确保开发环境与生产环境示例配置不缺关键字段。

输出物：

- 前端环境说明。
- 前端启动与构建命令说明。

完成定义：

- `npm run dev` 与 `npm run build` 均可成功执行。

## 6.7 工作包 G：测试基座建设

目标：

- 为后续阶段建立固定测试入口和最小可执行样例。

具体任务：

- 明确后端测试分层：
  - `tests/api/`
  - `tests/services/`
  - `tests/queries/`
- 增加最小冒烟测试用例，至少覆盖：
  - 应用启动
  - 健康检查接口
  - 数据库迁移执行
- 明确前端本阶段仅要求构建测试；组件测试与页面交互测试放到后续阶段扩展。
- 明确测试数据策略：
  - 阶段一只使用空库或最小基线数据
  - 不引入大规模模拟数据

输出物：

- 最小测试说明。
- 可执行的后端冒烟测试样例。

完成定义：

- 执行测试命令后能得到明确的通过/失败结果。

## 6.8 工作包 H：文档与目录职责收口

目标：

- 保证文档、目录结构和实际仓库状态一致。

具体任务：

- 校验 README 是否准确反映当前仓库可执行能力。
- 在 `docs/` 下增加阶段一执行与验收文档。
- 明确 `scripts/`、`data/`、未来 `deploy/` 的职责与当前状态。
- 在文档中说明当前哪些能力已实现、哪些仍是后续阶段内容，避免误判完成度。

输出物：

- 更新后的项目说明文档。
- 阶段一详细文档。

完成定义：

- 文档阅读者能够准确理解当前仓库“能做什么、不能做什么、下一步做什么”。

## 7. 推荐执行顺序

建议按以下顺序推进实施：

1. 工作包 A：环境与依赖收口
2. 工作包 B：数据库初始化链路收口
3. 工作包 C：后端启动基线收口
4. 工作包 D：统一错误响应与基础接口约定收口
5. 工作包 E：日志与可观测性最小基线
6. 工作包 F：前端开发基线收口
7. 工作包 G：测试基座建设
8. 工作包 H：文档与目录职责收口

原因：

- 先收口环境与数据库，才能稳定启动应用。
- 先固定错误和日志规范，后续阶段实现业务时不会反复返工。
- 先做最小测试基座，后续阶段每完成一块能力都可以直接挂接进来。

## 8. 阶段一验收标准

阶段一完成时，必须同时满足以下条件：

### 8.1 环境与启动验收

- 后端依赖能按文档安装成功。
- 前端依赖能按文档安装成功。
- PostgreSQL 与 Redis 的本地开发配置明确。
- 后端可在本地启动。
- 前端可在本地启动。

### 8.2 数据库验收

- 空数据库可通过 Alembic 完成结构初始化。
- 初始化后的表、索引、扩展、触发器与设计文档一致。
- 独立 SQL 初始化脚本可作为备用初始化路径使用。

### 8.3 接口基线验收

- `/api/v1/health/` 返回 200。
- 返回结构符合约定。
- 基础错误响应格式已在文档中固定，并至少在一个公共入口中可复用。

### 8.4 工程规范验收

- README 与实际执行命令一致。
- 环境变量模板完整。
- 基础目录职责说明清晰。
- 阶段一边界明确，不与后续业务功能混淆。

### 8.5 测试基线验收

- 后端至少存在一条可执行冒烟测试。
- 数据库迁移至少存在一次实际验证记录。
- 前端至少完成一次构建验证。

## 9. 测试计划与用例

## 9.1 后端启动冒烟测试

测试目标：

- 验证 FastAPI 基础工程能够正常启动。

前置条件：

- `backend/.env` 配置完成。
- PostgreSQL 实例可访问。

执行步骤：

1. 安装后端依赖。
2. 在 `backend/` 目录执行 `uvicorn app.main:app --reload --host 0.0.0.0 --port 8000`。
3. 观察启动日志。

预期结果：

- 启动过程无导入错误、配置错误、数据库初始化错误。
- 服务监听成功。

## 9.2 健康检查接口测试

测试目标：

- 验证基础探活接口可用。

执行步骤：

1. 启动后端服务。
2. 访问 `GET /api/v1/health/`。

预期结果：

- 返回 HTTP 200。
- 返回 JSON 至少包含 `status` 字段。
- 返回结构稳定，不依赖业务数据。

## 9.3 数据库迁移测试

测试目标：

- 验证数据库初始化流程可重复。

执行步骤：

1. 准备空数据库。
2. 执行 `cd backend && alembic upgrade head`。
3. 查询数据库中的表、索引和触发器。

预期结果：

- 迁移执行成功。
- `alembic_version` 存在且版本正确。
- 基础业务表和索引存在。

## 9.4 SQL 初始化脚本测试

测试目标：

- 验证备用初始化路径可用。

执行步骤：

1. 准备另一空数据库或重建测试库。
2. 执行 `psql -h localhost -U postgres -d family_tree_db -f scripts/sql/family_tree_init.sql`。

预期结果：

- 执行成功，无关键对象缺失。
- 表、索引、扩展和触发器创建完整。

## 9.5 前端构建测试

测试目标：

- 验证前端工程基础可构建。

执行步骤：

1. 安装前端依赖。
2. 执行 `cd frontend && npm run build`。

预期结果：

- 构建成功。
- 无缺失环境变量导致的阻塞性报错。

## 9.6 配置模板测试

测试目标：

- 验证 `.env.example` 可用于初始化本地配置。

执行步骤：

1. 基于模板复制 `.env`。
2. 按 README 最小要求填写配置。
3. 启动前后端。

预期结果：

- 模板字段完整，不需要额外猜测关键配置项。

## 9.7 错误响应结构测试

测试目标：

- 验证统一错误响应设计已落地到基础入口或公共能力。

执行步骤：

1. 人为制造一个基础错误场景，例如访问不存在路由或未满足接口输入要求。
2. 检查响应结构。

预期结果：

- 错误结构符合文档约定，至少具备可推广的统一格式。

## 10. 阶段一完成后的状态定义

阶段一完成后，项目应处于以下状态：

- 仓库可以作为团队统一开发起点。
- 任何阶段二开发工作都不需要再讨论环境搭建、表结构初始化、基础探活和最小测试入口。
- 后续所有 API 和页面都可以直接基于既定目录、既定配置、既定错误结构和既定测试基线扩展。

换句话说，阶段一完成的标志不是“功能多”，而是“基线稳”。

## 11. 后续衔接

阶段一完成后，下一阶段应直接进入“阶段二：认证与权限闭环”，重点推进以下内容：

- 用户注册与登录
- JWT Access/Refresh Token 闭环
- 当前用户获取
- 基础鉴权依赖
- 族谱角色权限判断入口

阶段二的详细文档应以本阶段输出的环境基线、错误结构和测试基座为前提继续展开。
