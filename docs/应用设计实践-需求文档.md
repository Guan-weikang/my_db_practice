# “应用设计实践”需求文档

## 1. 文档目的

本文档用于将《第06章 数据库应用实践》课件中“应用设计实践”部分的内容整理为可长期查阅的 Markdown 版本，作为后续系统设计、实现、演示和验收的统一参考依据。

本文档仅描述业务场景、任务要求、验收要求和提交材料，不展开具体实现方案，不限定最终技术细节，不替代后续设计文档、数据库设计文档或实现说明。

## 2. 项目概述

- 项目名称：寻根溯源族谱管理系统
- 项目性质：数据库应用实践作业
- 项目目标：围绕族谱管理业务场景，完成数据库建模、数据组织、查询分析、图形化应用展示以及性能优化相关任务

系统需要面向多用户使用场景，支持多个族谱并行管理，能够记录家族成员信息、成员间关系以及基础统计信息，并支持围绕族谱结构的查询、展示和分析。

## 3. 业务场景说明

系统中需要管理多个族谱，每个族谱对应一个家族。每个族谱至少应记录以下基本信息：

- 谱名
- 姓氏
- 修谱时间
- 创建用户

系统支持多用户。每个用户可以创建自己的族谱，也可以邀请其他用户参与自己创建的族谱内容维护。用户只能看到和操作自己创建的族谱，以及被邀请参与的族谱。

族谱中需要记录家族成员的基础信息，包括但不限于：

- 姓名
- 性别
- 生卒年
- 生平简介

系统还需要记录成员之间的关系，至少包括：

- 血缘关系：父子、父女、母子、母女
- 婚姻关系

该业务场景具备明显的层级结构和图结构特征，既需要支持基本数据管理，也需要支持递归查询、路径查询和统计分析。

## 4. 建设目标与核心挑战

本任务围绕族谱数据组织与查询能力展开，核心目标包括：

- 建立一套可管理多族谱、多用户协作的数据组织方案
- 支持成员及关系信息的录入、维护、查询和展示
- 支持面向族谱结构的祖先追溯、后代查询和亲缘路径分析
- 在大规模模拟数据下完成查询功能与性能验证

需要重点应对以下业务挑战：

1. 成员之间的层级关系深度不确定，不能仅依赖固定层数设计。
2. 可能存在同名同姓但不同辈分、不同分支的成员，查询不能简单依赖姓名唯一性。
3. 需要快速查询某个成员的所有直系后代，或向上追溯其祖先链路。
4. 需要快速判断两个人之间是否存在亲缘关系，并在存在关系时给出对应的亲缘链路。

## 5. 功能需求

### 5.1 用户注册与登录

- 系统应支持用户注册。
- 系统应支持用户登录。
- 系统应基于登录用户控制可见数据范围。

### 5.2 用户可见范围与权限边界

- 用户只能看到自己创建的族谱。
- 用户应能看到被其他用户邀请参与维护的族谱。
- 用户只能操作自己创建的或者被授权参与的族谱及其成员数据。

### 5.3 Dashboard 统计展示

系统应提供基础统计展示界面，至少包括：

- 家族总人数
- 男女比例

Dashboard 的统计结果应能够针对具体族谱进行展示，并与数据库中的实际数据保持一致。

### 5.4 族谱管理

系统应支持族谱的基础管理操作，至少包括：

- 创建族谱
- 查看族谱
- 修改族谱
- 删除族谱

系统应支持族谱协作能力，即族谱创建者能够邀请其他用户参与该族谱内容维护。

### 5.5 成员管理

系统应支持家族成员信息的基础管理操作，至少包括：

- 新增成员
- 查看成员
- 修改成员
- 删除成员

成员管理应覆盖成员的基础属性信息及其在族谱中的关系信息维护。

### 5.6 成员查找

- 系统应支持按成员姓名进行模糊查找。
- 模糊查找结果应能够区分重名成员，避免仅凭姓名导致识别错误。

### 5.7 树形预览

- 系统应支持以层级结构或缩进列表的方式展示某个分支的人物关系树状图。
- 树形预览应能够反映成员之间的上下代关系。

### 5.8 祖先查询

- 系统应支持输入一个人物的 ID。
- 系统应以树状图形式展示该人物父辈及更高层级的祖先信息。
- 该功能应能够适应不固定深度的祖先追溯场景。

### 5.9 亲缘关系查询

- 系统应支持输入两个人物的 ID。
- 系统应判断两者之间是否存在由亲缘关系连接而成的通路。
- 若存在通路，系统应展示对应的亲缘链路。

## 6. 数据建模与规范化要求

### 6.1 概念建模

- 需要绘制 ER 图。
- ER 图应识别出核心实体及其属性。
- ER 图应明确实体之间的联系类型，如 1:1、1:N、M:N。

ER 图中至少应覆盖成员、族谱、用户、关系等业务对象。若建模中引入其他辅助实体，也应保持与业务场景一致。

### 6.2 关系模式转换

- 需要将 ER 图转换为关系模式。
- 关系模式应能够完整支撑业务场景与查询需求。
- 需要说明各关系模式达到的范式级别。

建议至少满足 3NF；若设计达到 BCNF，可作为更优结果进行说明。

### 6.3 约束设计

需要在关系模型中定义必要约束，至少包括：

- 主键约束
- 外键约束
- `CHECK` 约束

约束设计应能够反映业务规则。示例要求包括但不限于：

- 父亲的出生年份必须早于子女

在实际设计中，可根据业务对象补充其他合理约束，但不应弱化课件中明确提出的约束要求。

## 7. 数据生成与导入导出要求

### 7.1 模拟数据生成

需要编写 Python 脚本或 SQL 存储过程生成模拟数据。

生成的数据应满足以下最低规模要求：

- 至少生成 10 个族谱
- 至少有 1 个族谱拥有 50,000 以上成员
- 整个系统中的模拟成员数据不少于 100,000 条
- 每一个族谱内的成员至少与另一个成员存在亲缘关系
- 单个族谱内至少模拟出 30 代人的传承关系

模拟数据需要能够支撑后续查询、统计、路径分析和性能测试任务。

### 7.2 数据导入与导出

需要演示批量数据导入与导出能力，至少包括：

- 使用 `LOAD DATA`（MySQL）或 `COPY`（PostgreSQL）将 CSV 数据批量导入数据库
- 导出某个分支的数据备份文件

若最终使用其他关系型数据库管理系统，应提供与上述能力等价的批量导入导出说明与操作结果。

## 8. SQL 核心任务要求

以下需求均应通过 SQL 完成，且每个需求应使用单个 SQL 实现。

### 8.1 基本查询

给定一个成员 ID，查询其：

- 配偶
- 所有子女

### 8.2 递归查询

编写递归公用表表达式（Recursive CTE），输入成员 A 的 ID，输出其向上追溯的所有历代祖先。

该项为核心任务之一，应能够体现层级递归查询能力。

### 8.3 统计分析一

统计某个家族中平均寿命最长的一代人（辈分）。

### 8.4 统计分析二

查询所有年龄超过 50 岁、且没有配偶的男性成员。

年龄判断按“当前日期减去出生日期”这一口径进行理解和计算。

### 8.5 统计分析三

找出家族中出生年份早于该辈分平均出生年份的所有成员。

## 9. 物理优化与索引要求

### 9.1 索引策略设计

需要针对以下需求设计合适的索引：

- 根据姓名进行模糊查询
- 根据父节点 ID 查询子节点

索引设计应与实际查询模式对应，能够服务于成员检索、树状结构查询和后代分析等场景。

### 9.2 性能对比与执行计划分析

需要记录在有索引和无索引两种情况下，执行以下查询时的性能差异：

- 查询某曾祖父的所有曾孙（四代查询）

除执行时间对比外，还需要提交执行计划分析结果，至少包括：

- `EXPLAIN` 输出结果
- 对性能差异的基本说明

## 10. 提交物要求

实验报告中至少应包含以下内容：

- ER 图
- 关系模型
- 对关系模型达到 3NF 的分析说明
- 已创建索引的说明
- 已设置约束的说明
- 数据生成方法说明（手工插入或自编工具）
- 所使用 RDBMS 的名称和版本说明
- 各查询需求对应的 SQL 语句
- SQL 在数据库中执行后的结果截图

若采用自编工具生成数据，还应提交该工具的源码。

除实验报告外，还应提交数据库导出文件。导出方式应使用所采用 RDBMS 自带的数据导出或数据库备份工具完成。

实验报告应重点体现个人实际完成的工作内容。

## 11. 演示与答辩验收要求

现场验收至少包括以下内容：

- 演示图形化界面中要求实现的各项功能
- 回答教师提出的相关问题

演示内容应能够覆盖用户登录、族谱管理、成员管理、统计展示、树形预览、祖先查询和亲缘关系查询等核心功能。

## 12. 交付成果验收要点

为便于后续自查，本项目的验收可按以下维度进行核对：

### 12.1 业务与功能完整性

- 是否完整覆盖用户、族谱、成员、关系管理场景
- 是否支持模糊查找、祖先查询、亲缘链路查询
- 是否具备基础图形化界面

### 12.2 数据与建模规范性

- 是否提交 ER 图与关系模型
- 是否说明范式级别
- 是否设置主键、外键和必要的 `CHECK` 约束

### 12.3 数据规模达标性

- 族谱数量是否不少于 10 个
- 是否至少有 1 个族谱成员数大于 50,000
- 系统总成员数是否不少于 100,000
- 单个族谱是否达到至少 30 代传承

### 12.4 查询与性能验证

- 是否完成规定 SQL 查询
- 是否使用单个 SQL 实现每项要求
- 是否完成索引前后性能对比
- 是否提交执行计划分析

### 12.5 材料提交完整性

- 是否提交实验报告
- 是否提交 SQL 结果截图
- 是否提交数据生成源码（如适用）
- 是否提交数据库导出文件
